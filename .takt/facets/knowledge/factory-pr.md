# 工場の PR・レビューView・CI の知識

工場の workflow が PR を出すときの決まり。PR の欄の正本は `.github/pull_request_template.md`、閉じるキーワードの検査は `tools/factory/checks/closing.mjs`。
レビューView とゲートごとの確認観点は、人がゲートを判定するときの手引き(スキル `gate-review`)と同じ内容にしている。

## PR の決まり

- PR は Draft で作る。マージ・Ready 化・承認は人がする
- `.github/pull_request_template.md` の欄をすべて埋める。当てはまらない欄は「なし」と書き、欄を消さない
- 工場の版は `.factory/VERSION` の中身。工場(`.takt/`)の最終コミットは `git log -1 --format=%h -- .takt/`
- プッシュと `gh pr create --base main` は別のコマンドにする。PR の本文・コメントの本文はリポジトリの外(`$TMPDIR` など)のファイルに書き、`--body-file` で渡す(コマンドの文字列に「git push」と「main」が並ぶとフックが誤って止めることがある)
- 1 作業項目 → 1 ブランチ → 1 PR。同じ実行の中で2回目以降に公開するときは、同じブランチ・同じ PR を更新する。PR を作り直さない
- PR を出したあとで中身が変わったら、PR の説明も合わせて直す(`gh pr edit <番号> --body-file <ファイル>`)

### 作業項目の参照

- `impl/` の PR: 本文に `Closes #n` と書く(マージで作業項目が閉じる)
- それ以外(`knowledge/` `req/` `spec/`)の PR: 本文に `Refs #n` と書く
- 閉じるキーワード(close・closes・closed・fix・fixes・fixed・resolve・resolves・resolved の後に `#番号`)は、`impl/` の PR の `Closes #n` 以外に書かない。「付けない」と説明する文の中でも書かない(GitHub は否定を読まずに閉じる。CI「作業項目を途中で閉じない」が落とす)。Issue へのコメントにも書かない

### PR テンプレートの欄

```markdown
## 工程

- 工程: <knowledge / req / spec / impl のどれか。[A]〜[D] の名前も添える>
- Refs #<n>        ← impl/ の PR では「Closes #<n>」

## 何をしたか

<変えたファイルと中身を表か箇条書きで>

## 前提

- premises: `.factory/premises/ISSUE-<n>.yml`(なければ「なし」)
- 要件:
- 仕様:
- ナレッジ:

## 工場の版

- `.factory/VERSION`:
- 工場(`.takt/`)の最終コミット:

## 実行環境

- エージェント・モデル:
- 実行場所:
- セッションの要約:

## レビューView

### 事実
### 理由
### 問い

## 介入の記録

| 種類 | 原因(ナレッジ / 要件 / 仕様 / 工場) | 内容 | 改善の Issue |
|---|---|---|---|

- 手で直した回数: 0
```

- 「介入の記録」の表は、人が記録した介入だけを書く。エージェントの作業(検証の差し戻し、続きでの手直し)は介入ではない。ただし人が CI の失敗を見て takt.sh をもう一度実行したことは、介入ではなく通常の運転。介入がなければ表の行を「なし」にする
- 「実行環境」には takt の工程の workflow(Knowledge・Requirements・Spec・Implement のどれか)で動いたことと、エージェント(環境変数 `FACTORY_AGENT` の値。claude・codex・copilot)、実行場所(ローカル・devcontainer など)を書く

## レビューView(事実・理由・問い)

判定者は 1 人で、すべての差分は読めない。差分を全部読まなくても判定できるようにする。

| 欄 | 書くこと | 書かないこと |
|---|---|---|
| 事実 | 何が変わったか。件数・数値・テストの結果・確かめた方法。確かめていないことは「未確認」と書く | 感想、「問題ありません」 |
| 理由 | なぜそうしたか。根拠の ID(`BR-…`・`FR-…`・`SPEC-…`・ADR・Issue の文) | 根拠のない「一般的に」 |
| 問い | 人に決めてほしいこと。Yes/No か選択肢で答えられる形。Yes のとき何が起きるかも書く | 「ご確認ください」だけの問い |

- 問いがなければ「なし」と書く。問いは多くても 3 つまでにし、残りは `knowledge/open-questions.md` に回す(上流の工程だけ)
- 数値は差分から数える(「業務ルール 14 件」「シナリオ 3 件追加」)。推測で書かない
- 失敗したこと・回避したこと(フックに止められた、CI を直した回数、検証の差し戻しの回数)も事実に書く

## ゲートごとの確認観点(人が判定で見ること。PR の事実に材料を出す)

### ゲート0(`knowledge/` の PR)

- 業務ルールの各 `sources` を開くと、ルールと同じことが書いてあるか
- `status: 確定` にしてよいもの(人が出どころと照らせたもの)だけが確定になっているか
- 未確定事項に、仮決めと「外れたら直す範囲」があるか。金額・税・権限・個人情報に仮決めがないか
- レビューView の「問い」に、確定させたいルールの一覧を出す

### ゲート1(`req/` の PR)

- 要件の検証役の結果が付いていて、指摘に対応したか
- 要件が EARS の 1 文で、参照する業務ルールがすべて確定か
- Issue の受け入れ条件案が、どれかの要件とシナリオになっているか(対応表を事実に書く)
- 画面の変更があれば、新しい状態の承認画像は人が撮る(PR の「問い」に「この状態の画面を撮って承認してほしい」と書く)
- マージしたら、人が `gate1-approved` を付け、列を `stage:着手待ち` にする

### ゲート2(`spec/` の PR)

- 要件 1 件ごとに、満たす API と処理ルールが決まっているか(対応表を事実に書く)
- 具体例の表に境界があり、各行のテストの観点があるか
- OpenAPI の差分が、既存のクライアント(画面)を壊さないか
- マージしたら、人が `gate2-approved` を付け、列を `stage:仕様確定` にする

### ゲート3(`impl/` の PR)

- CI の必須チェックがすべて成功しているか
- 実装の検証役の結果が付いていて、「直す」の指摘に対応したか
- 仕様の具体例・シナリオとテストの対応表が「なし」0 件か
- `.factory/premises/ISSUE-<n>.yml` があり、main の版と一致しているか

## CI

- CI は `.github/workflows/ci.yml`(バックエンド・フロントエンド・Vitest・ブラウザE2E・メトリクス・ミューテーション)と、工場のゲート `.github/workflows/factory.yml`(フックの確認、検査スクリプトのテスト、画面の差分、role-guard・gate-check・閉じるキーワードなどのゲートの検査)
- PR では、変えた場所に応じてジョブを飛ばす(最初のジョブ「変えた場所の判定」が決める。正は `tools/factory/lib/ci-scope.mjs`)。`knowledge/`・`requirements/`(screens 以外)・`specs/`・`docs/`・`.factory/`・`*.md` だけを変えた PR では、工場のゲートの検査だけが動く。飛ばしたジョブ(skipped)は、必須チェックとしては通ったものとして扱われる
- mutation は非ブロッキング(Stryker 自体の失敗だけが赤)
- 工場の workflow は CI を待たない。人が結果を見て、落ちていたら `tools/factory/takt.sh <n>` をもう一度実行する。書く step が「続き」として、`gh pr checks <番号>` と `gh run view <run-id> --log-failed` で原因を読んで直す
- 「ゲートラベルの確認」は、その工程までのゲートラベルがすべてそろい、ゲートラベルの工程の PR(`req/<n>-…`・`spec/<n>-…`)がマージ済みであることを確かめる。人がゲートラベルを付けたあとに再実行するもの。エージェントはゲートラベルを変えない
- CI の再実行や例外の判断(CI の承認)は人の介入。エージェントは CI を再実行しない
- `gh` はリポジトリのディレクトリで実行する
- `git push -u origin <branch>`。ネットワークエラーのときだけ指数バックオフで最大4回やり直す
