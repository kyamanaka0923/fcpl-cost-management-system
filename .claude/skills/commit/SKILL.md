# コミットスキル

**利用モデル**: 変更の意図を読み取って分割する判断を伴うため `claude-sonnet-5`。
1ファイルの明白な修正を1コミットにするだけなら `claude-haiku-4-5` で可。

**このスキルはコミットまで**。プッシュと CI 確認は ci-and-env スキルに従う。

## 手順(この4段階を必ず順に踏む)

### 1. 変更の全体を見せる

推測でコミットしない。**まず全部見せてから**判断する。

```bash
git status --short              # 変更・未追跡の一覧
git diff --stat                 # 変更量の把握
git diff                        # 追跡済みファイルの差分(全体)
git diff --staged               # 既にステージ済みがあれば
git log --oneline -10           # 直近の書き方を確認してから文面を決める
```

- **未追跡ファイル(`??`)は `git diff` に出ない**。新規ファイルは必ず中身を確認する
  (`git status --short` で `??` を拾い、該当ファイルを Read する)。
  「差分を見せた」と言いながら新規ファイルを見ていない、が最も多い漏れ
- 差分が大きいときは `--stat` で全体像を出したうえで、意味のあるファイルの差分を提示する。
  **省略したら省略したと明示する**(黙って一部だけ見せない)
- 生成物・セッション固有の変更が紛れていないか確認する。混ざりやすいもの:
  `bin/` `obj/` `StrykerOutput/` `frontend/node_modules/` `playwright-report/` `test-results/`、
  `.claude/settings.local.json` に自動追加された一時パス入りの権限エントリ

### 2. 意味のある単位に分ける

**分割の軸は「目的」であって、層やファイル種別ではない。**
このリポジトリでは1つの機能変更がドメイン〜フロント〜テスト〜ドキュメントに及ぶが、
それは**1コミット**にまとめる(履歴の Issue #5〜#9 がその形)。

| 分ける | 分けない |
|---|---|
| 別の Issue・別の目的の変更 | 同じ目的の層またぎ(Domain / Application / Infrastructure / WebApi / frontend) |
| ついでに直した無関係な設定・タイポ | 実装とそのテスト |
| 独立して意味を持つリファクタ | 実装とそれに伴う README / MANUAL / DESIGN の同期 |
| スキル・CI 設定など運用面の変更 | 実装とスキーマ移行 |

- 迷ったら**まとめる**。「1つの変更として説明できるか」が基準
- ステージングは対象を明示する。`git add -A` で一括投入しない
  (意図しないファイルが混ざる。`git add <path>...` で指定する)

### 3. メッセージを起案する

**コミットメッセージは日本語**(CLAUDE.md の絶対ルール)。

```
<種別>: <何が変わるかの要約(50字程度・体言止めか「〜する」)>

<なぜそうしたか。解決した問題・きっかけ・前提を1〜3行>

- <変更点を層や観点ごとに。判断の理由も添える>
- <テストで担保したこと>
- <同期したドキュメント>

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

#### 種別(履歴で実際に使われているもの)

| 種別 | 使う場面 |
|---|---|
| `Issue #N:` | GitHub Issue への対応(**Issue があれば最優先でこれ**) |
| `[refactor]` | 挙動を変えない整理・コメント追加 |
| `[config]` | CLAUDE.md・スキル・権限などの設定 |
| `ドキュメント:` | README / MANUAL / DESIGN の更新 |
| `CI:` / `E2E:` | ワークフロー・ブラウザE2E |
| `スキル:` / `スキル追加:` | `.claude/skills/` の変更 |

種別に迷ったら、素の日本語要約でよい(履歴にも前置きなしの例が多数ある)。
Conventional Commits の `feat:` / `fix:` / `docs:` / `refactor:` / `ci:` / `chore:` を使いたい場合は、
上の表がその対応表にあたる。**ただし既存40コミットの書式に合わせることを優先する**
(型接頭辞 + 要約 + 「なぜ」の本文、という Conventional Commits の骨格は上の形式で満たしている)。

#### 「何を」ではなく「なぜ」を書く

本文が diff を日本語に訳しただけなら書く価値がない。差分を読めば分かることではなく、
**差分からは読み取れないこと**を書く。

| 書かない(何を) | 書く(なぜ) |
|---|---|
| `SumByCategoryAsync` を追加 | 課ごとに集約を復元すると課数×明細数に比例して遅くなるため、明細を読まない集計経路を追加 |
| インデックスを追加 | 最新の承認済みバージョンの絞り込みが毎回フルスキャンになっていたため |
| テストを3件追加 | 空リストで `IN ()` が SQL エラーになる経路を踏んでいたため、その分岐を固定 |

- 検討して**採らなかった案**があれば1行残す(後から同じ道を試させないため)
- 計測値・テスト件数など**確かめた事実**は具体的に書く。確かめていないことは書かない
- 破壊的変更・スキーマ変更・移行が必要な点は本文に必ず明記する

### 4. 確認を取ってからコミットする

**確認なしにコミットしない。** 起案がそろったら、実行前に次をまとめて提示する。

1. コミットの分割案(何番目のコミットにどのファイルが入るか)
2. 各コミットのメッセージ全文
3. 除外したファイルとその理由(生成物・未完成の変更など)

そのうえで「この内容でコミットしてよいか」を聞き、**承認を得てから** `git add` / `git commit` を実行する。
修正の指示が来たら、直してもう一度確認する。

コミット後は `git log --oneline -<件数>` と `git status` で結果を報告する。

## やってはいけないこと

- **確認前のコミット**。分割案とメッセージを見せる前に `git commit` を打たない
- **プッシュ**。明示的に依頼されていない限りプッシュしない(ci-and-env スキル)。
  ブランチは `claude/cost-management-system-qvc368`、**main へ直接コミット・プッシュしない**
- **`git commit --no-verify`**。フックを迂回しない
- **push 済みコミットへの `--amend` / force push**。未 push の直前コミットのみ、依頼があれば可
- **`git add -A` / `git commit -a`** による一括投入
- **`git checkout` / `git restore` / `git reset --hard` で未コミットの変更を捨てる**こと。
  依頼されていない限り作業ツリーを壊さない
- **対話的フラグ**(`git rebase -i` / `git add -i`)。この環境では動かない
