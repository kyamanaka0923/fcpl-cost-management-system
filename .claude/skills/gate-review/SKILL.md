# ゲートのレビューView

判定者は 1 人で、すべての差分は読めない。PR の「レビューView」で、差分を全部読まなくても判定できるようにする。
**承認 = 人が PR を main にマージすること。** ゲート0〜2 の通過は、人が Issue にゲートラベルを付けて表す。

## レビューView の 3 つ

| 欄 | 書くこと | 書かないこと |
|---|---|---|
| 事実 | 何が変わったか。件数・数値・テストの結果・確かめた方法。確かめていないことは「未確認」と書く | 感想、「問題ありません」 |
| 理由 | なぜそうしたか。根拠の ID(`BR-…`・`FR-…`・`SPEC-…`・ADR・Issue の文) | 根拠のない「一般的に」 |
| 問い | 人に決めてほしいこと。**Yes/No か選択肢で答えられる形**。Yes のとき何が起きるかも書く | 「ご確認ください」だけの問い |

- 問いがなければ「なし」と書く。問いは多くても 3 つまでにし、残りは `knowledge/open-questions.md` に回す
- 数値は差分から数える(「業務ルール 14 件」「シナリオ 3 件追加」)。推測で書かない
- 失敗したこと・回避したこと(フックに止められた、CI を再実行した)も事実に書く

## ゲートごとの確認観点

### ゲート0(ナレッジ。`knowledge/<n>-…` の PR)

- 業務ルールの各 `sources` を開くと、ルールと同じことが書いてあるか
- `status: 確定` にしてよいもの(人が出どころと照らせたもの)だけが確定になっているか
- 未確定事項に、仮決めと「外れたら直す範囲」があるか。金額・税・権限・個人情報に仮決めがないか
- レビューView の「問い」に、確定させたいルールの一覧を出す

### ゲート1(要件・画面。`req/<n>-…` の PR)

- `requirements-reviewer` のコメントが付いていて、指摘に対応したか(対応しない指摘は理由を書く)
- 要件が EARS の 1 文で、参照する業務ルールがすべて確定か
- 要求(Issue)の受け入れ条件案が、どれかの要件とシナリオになっているか(対応表を事実に書く)
- マージしたら、人が `gate1-approved` を付け、列を `stage:着手待ち` にする

### ゲート2(仕様。`spec/<n>-…` の PR)

- 要件 1 件ごとに、満たす API と処理ルールが決まっているか(対応表を事実に書く)
- 具体例の表に境界があり、各行のテストの観点があるか
- OpenAPI の差分が、既存のクライアント(画面)を壊さないか
- マージしたら、人が `gate2-approved` を付け、列を `stage:仕様確定` にする

### ゲート3(実装。`impl/<n>-…` の PR)

- CI の必須チェックがすべて成功しているか
- `code-reviewer` のコメントが付いていて、「直す」の指摘に対応したか
- 仕様の具体例・シナリオとテストの対応表が「なし」0 件か
- `.factory/premises/ISSUE-<n>.yml` があり、main の版と一致しているか
- 介入の記録があれば、原因を直す Issue(工場の改善)が起票されているか

## PR の説明を直すとき

PR を出したあとで中身が変わったら(問いに回答が来た、コミットを足した)、説明も合わせて直す。
回答は PR にコメントで残す(判定の記録になる)。
