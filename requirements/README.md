# 要件(requirements/)

工程 [B] の成果物。[ナレッジ](../knowledge/README.md)を入力にして、システムが**何をするか**を EARS で書く
(PROC-DEV-001 3.1、[ADR-0015](../docs/adr/0015-software-factory.md))。
ゲート1 の承認は、ここを変える PR(`req/<n>-…` ブランチ)を人がマージし、Issue に `gate1-approved` を付けること。

## 置き場

```
requirements/
  README.md            この文書
  <領域>/FR-x.y.md     要件 1 件 = 1 ファイル
  screens/             画面要件(フェーズ5 で作る)
```

| 領域 | 章 | 中身 |
|---|---|---|
| `organization/` | FR-1 | 部・課 |
| `project/` | FR-2 | 案件マスタ |
| `cost-element/` | FR-3 | 費目マスタ |
| `budget/` | FR-4 | 半期予算の策定 |
| `approval/` | FR-5 | 予算の承認・改定 |
| `actual/` | FR-6 | 実績計上 |
| `variance/` | FR-7 | 差異分析 |
| `profit/` | FR-8 | 損益分析 |
| `comparison/` | FR-9 | 予算バージョン比較 |
| `division/` | FR-10 | 部集計・部承認 |

ディレクトリは、最初の要件を移すときに作る。

## 段階的に移す

- 要件は**作業項目で触ったものから**移す。全部を先に移さない
- 移した要件は、[docs/REQUIREMENTS.md](../docs/REQUIREMENTS.md) の表の「状態」に `→ requirements/<領域>/FR-x.y.md` と書く。
  移した後は `requirements/` が正で、REQUIREMENTS.md の行は書き換えない
- 非機能要件(NFR)・アーキテクチャ制約(AC)は、当面 REQUIREMENTS.md に残す

## ID

- 既存の ID(`FR-4.8`、`FR-4.4a` など)はそのまま使う。Issue やコメントとの対応を保つため
- 新しい要件は、章の最後の番号の次を使う(`FR-4.10`、`FR-4.11` …)
- 既存の 1 行に応答が 2 つ以上あるとき(下の「1 文 1 応答」)は、`FR-4.4a-1`、`FR-4.4a-2` のように枝番を付けて分ける。
  枝番を付けたら、元の ID だけのファイルは作らない
- 廃止した ID は使い回さない。ファイルは消さずに `status: 廃止` にする

## 機械の検査

このディレクトリは、CI(`.github/workflows/factory.yml`。中身は [tools/factory/](../tools/factory/README.md))が検査する。
手元では `node tools/factory/cli.mjs ears` のように実行できる。

| 検査 | 見ること |
|---|---|
| 要件の書式(EARS) | frontmatter、ID とファイル名・領域、要件文が 5 文型の 1 文 1 応答か |
| 曖昧語の検査 | 禁止語 |
| 要件とシナリオの網羅 | 移した要件にシナリオがあるか、孤児のタグがないか、`ルール:` の文が要件文と同じか |
| ナレッジの出どころと確定 | `business_rules` が確定した業務ルールだけか |

## ファイルの形

```markdown
---
id: FR-4.8
title: 明細の金額は 0 以上
priority: Must              # Must | Should | Could(MoSCoW)
status: 有効                # 有効 | 廃止
business_rules: [BR-BUD-007]  # 使う業務ルール。status: 確定 のものだけ
screens: []                 # 関係する画面(SCR-…)。フェーズ5 以降
issues: [46]                # この要件を作った・変えた作業項目
---

## 要件

もし明細の金額が 0 未満ならば、システムは、その明細の保存を拒否する。

## 補足

要件文の読み方の補足だけを書く。新しい決まりを足さない(決まりは業務ルールに書く)。
```

- `business_rules` には [knowledge/business-rules/](../knowledge/business-rules/) の `status: 確定` のルールだけを書く。
  未確定のルールが要るなら、先にナレッジを確定させる(ゲート0)
- 数値の境界や例は、業務ルールの「例」と `.feature` のシナリオに書く。要件文には書き写さない

## EARS の 5 文型

要件文は次のどれか 1 つの形で書く。主語は「システムは、」に固定する。

| 文型 | 形 | 例 |
|---|---|---|
| 普遍 | `システムは、<応答>。` | システムは、課の区分合計を明細の合計として算出する。 |
| イベント駆動 | `<事象>とき、システムは、<応答>。` | 改定版が承認されたとき、システムは、同じ課と半期の旧承認版を失効にする。 |
| 状態駆動 | `<状態>間、システムは、<応答>。` | 予算が承認済みである間、システムは、その予算の明細の変更を拒否する。 |
| 望まれない振る舞い | `もし<条件>ならば、システムは、<応答>。` | もし明細の金額が 0 未満ならば、システムは、その明細の保存を拒否する。 |
| オプション | `<機能>を含む場合、システムは、<応答>。` | 期間費用の明細が明細名を含む場合、システムは、費目合計を明細の合計として算出する。 |

- 前置き(`<事象>とき`、`<状態>間` など)は、組み合わせてよい。例: `予算がドラフトである間、明細が保存されたとき、システムは、…`
- **1 文 1 応答。** 「〜し、〜する」「〜かつ〜する」のように応答を 2 つ書かない。2 つあるなら要件を分ける。
  機械で確かめられるように、**応答(「システムは、」より後ろ)には読点「、」と「かつ・および・並びに」を置かない**
- 応答は、外から確かめられる振る舞いにする(画面・API の結果・保存された値)。実装の方法(テーブル・クラス)を書かない

## 禁止語

意味が人によって変わる語は使わない。一覧は [tools/factory/ambiguity-words.txt](../tools/factory/ambiguity-words.txt)
(CI の「曖昧語の検査」が、要件・業務ルール・`.feature` の `ルール:` 行を検査する)。

| 使わない | 代わりに |
|---|---|
| 適切に・正しく | 何をもって正しいかを業務ルールで決め、そのルールを参照する |
| など・等 | すべて列挙する。列挙できないなら、問いにする |
| 速やかに・すぐに | 時間を数値で書く(NFR)か、書かない |
| 必要に応じて・場合によっては | 条件を書き出して、望まれない振る舞い・状態駆動の文型にする |

## 受け入れ条件(.feature)

受け入れ条件は、既存の日本語 Gherkin を正にする。置き場所は動かさない([ADR-0016](../docs/adr/0016-test-scope-layout-and-frontend-unit.md))。

- `tests/integration/backend/Application/Features/*.feature`(ユースケース)
- `tests/e2e/api/Features/*.feature`(API)
- `tests/e2e/browser/features/*.feature`(画面)

要件を移したら、その要件を確かめる `ルール:` に**要件文をそのまま書き**、`@FR-x.y` タグを付ける。
業務ルールの代表例を確かめるシナリオには `@BR-…` も付けてよい。

```gherkin
  @FR-4.8 @BR-BUD-007
  ルール: もし明細の金額が 0 未満ならば、システムは、その明細の保存を拒否する。

    シナリオ: 金額が -1 円の明細は保存できない
      …
```

- `ルール:` に付けたタグは、その下のシナリオすべてに付く(Reqnroll で確認済み)
- 1 つの `ルール:` には 1 つの要件。1 つの要件は、複数の `.feature`(ユースケースと画面など)の `ルール:` から確かめてよい
- 移した要件には、シナリオが 1 つ以上要る。存在しない要件を指すタグは置かない(CI の「要件とシナリオの網羅」が検査する。`ルール:` の文が要件文と一字一句同じかも見る)
- まだ移していない要件の `ルール:` は、今の短い見出しのままでよい
