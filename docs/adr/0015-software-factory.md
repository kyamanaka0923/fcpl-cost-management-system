# ADR-0015: ソフトウェアファクトリーを導入し、ゲートをハーネスで強制する

- 状態: Accepted
- 日付: 2026-10-26

## 背景

AI が生成・検証を担い、人が「何を作るか」と「出してよいか」を決める開発の形(ソフトウェアファクトリー)を、
このリポジトリで動かす。元になる文書は `software-factory/` にある。

- `AI駆動ソフトウェア開発プロセス定義書.md`(PROC-DEV-001 v2.7): 工程・ゲート・判定者・成果物・証跡を決める
- `ソフトウェアファクトリー導入計画 ― 1か月で1機能をラインに通す.md`: それをどう回すかを書く
- `ソフトウェアファクトリーの概要 ― 工場の仕組みとロール.md`: 全体像

定義書の原則は「**決めるのは定義書、強制するのはハーネス**」。人の関与の仕方は、文書で決めるだけでは守られない。
ただし定義書と導入計画は、次を前提にしている。

- **GitHub Copilot cloud agent** で動かす
- **工場長と Outcome Owner を別の人**にし、CODEOWNERS の必須レビューでゲートを強制する
- 新規案件のリポジトリを、最初から工場の形で切る

このリポジトリは、どれとも違う。

- Claude Code のスキルで回している
- 判定者は 1 人
- 約 100 件の要件(`docs/REQUIREMENTS.md`)と、日本語 Gherkin のテストを持つ既存のプロダクトである

## 決定

### 1. 工程とゲート

定義書 2.1〜2.4 の工程とゲートをそのまま採る。

```
上流:   [A] ナレッジ ─▶ ゲート0 ─▶ [B] 要件・画面 ─▶ ゲート1(投入ゲート)
本ライン: 着手待ち ─▶ [C] 仕様 ─▶ ゲート2 ─▶ [D] 実装 ─▶ [E] 検証 ─▶ ゲート3(マージ)
```

すべてのゲートで、承認されるまで次の工程に進まない。

### 2. 定義書・導入計画との違い

| 論点 | 定義書・導入計画 | この工場 | 理由 |
|---|---|---|---|
| エージェント | Copilot cloud agent(`.github/agents/`) | **Claude Code**(`.claude/agents/`・スキル)。ローカルの devcontainer で動かす(導入計画 §16 のローカル版) | 既存のスキルと運用を活かす。共通の指示は `AGENTS.md` に置き、Copilot に移るときに使い回す |
| ゲートの強制 | CODEOWNERS の必須レビュー | **承認 = 人が main へマージすること**(導入計画 §17.1)。ゲート0〜2 の通過は Issue の**ゲートラベル**(`gate0-approved` など)で表す | 判定者が 1 人で、GitHub では PR の作者が自分の PR を承認できないため、必須レビューは使えない |
| エージェントの守り | cloud agent の仕組み(`copilot/…` にしか書けない、ドラフトのまま) | `.claude/settings.json` の `permissions.deny` と PreToolUse フック(`.claude/hooks/guard.sh`)で、マージ・Ready 化・承認・ゲートラベルの付け外し・main への push・承認した画面の書き換えを止める。main はルールセットでも守る | ローカルの Claude Code は人の資格情報で動くので、仕組みで止めないと、エージェントが自分でゲートを通せてしまう |
| Gherkin のキーワード | 英語(Feature / Rule / Scenario…) | **日本語のまま**(`# language: ja`)。要件文は `ルール:` の行に EARS で書き、`@FR-x.y` タグを付ける | 既存のシナリオとステップ定義がすべて日本語。混ぜると読みにくい |
| 要件の移し方 | 新規案件なので最初から EARS | **触る機能から段階的に**移す。未移行の要件は `docs/REQUIREMENTS.md` を出どころとして残す | 定義書 3.0「作業項目に必要な分だけ作る」に合わせる |
| 工場の版 | `factory.lock`(共通リポジトリから取り込んだ版) | `.factory/VERSION` と `.factory/CHANGELOG.md` | リポジトリが 1 つの段階なので、取り込む版がない |

### 3. ブランチ

`main` を正にし、作業ブランチを工程ごとに分ける。

| ブランチ | 工程 |
|---|---|
| `knowledge/<n>-*` | [A] ナレッジ |
| `req/<n>-*` | [B] 要件・画面 |
| `spec/<n>-*` | [C] 仕様 |
| `impl/<n>-*` | [D] 実装 |
| `prep/<n>-*` | 下ごしらえ |
| `factory/*` | 工場の変更 |

これまでの作業ブランチ `claude/cost-management-system-qvc368` は使わない。

### 4. 段階的に入れる

工場は段階的に入れる。各段階は 1 つの `factory/*` の PR にする。

- フェーズ0: 基盤
- フェーズ1: ナレッジ
- フェーズ2: 要件・仕様の型
- フェーズ3: エージェント
- フェーズ4: ゲートの CI
- フェーズ5: 画面要件
- フェーズ6: 計測
- フェーズ7: 実行環境
- フェーズ8: 初物検査

## 結果

- エージェントは、マージとゲートラベルを自分で操作できない。ゲートを通すのは、常に人の操作になる
- 判定者が 1 人なので、「生成と検証の分離」は人の側では成り立たない。AI の側で分ける(書くエージェントとレビューするエージェントを別にする)。人の判定の独立性は、判定者が増えたときに CODEOWNERS と必須レビューを足して補う
- フックは、コマンドの文字列で判定する。だから `gh pr merge` を grep するだけのコマンドも止まる(誤検知は許容する)。逆に、文字列を組み立てて実行する形のすり抜けは防げない。最後の守りは main のルールセットに置く
- フックとパーミッションを変えることは、工場の変更になる(`factory/*` ブランチで、人がマージする)
