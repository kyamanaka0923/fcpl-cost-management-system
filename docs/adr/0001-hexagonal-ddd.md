# ADR-0001: ヘキサゴナルアーキテクチャ + DDD 戦術パターンの採用

- 状態: Accepted
- 日付: 2026-07 頃(初期構築時)

## 背景

原価管理の業務ルール(承認フロー・不変条件・差異/損益の計算規則)は複雑で、
今後も要件変更が続くことが見込まれた(実際に「プロジェクト単位 → 課 × 半期」の大規模変更が発生している)。
業務ルールを永続化技術や UI・フレームワークから隔離し、変更の影響を局所化する必要があった。

## 決定

- **ヘキサゴナル(ポート & アダプタ)アーキテクチャ**を採用する。層は Domain / Application / Infrastructure / WebApi。
- 依存は常に内側(Domain)へ向ける。**Domain は他のどの層にも依存しない**。
- リポジトリは Domain 層に**ポート(interface)**として定義し、実装は Infrastructure 層のみに置く(DI で注入)。
- **DDD 戦術パターン**を用いる: 集約ルート・エンティティ・値オブジェクト・ドメインサービス・ドメイン例外。
  - 集約ルート/エンティティ/ドメインサービスは `sealed`、値オブジェクトは `readonly record struct`。
  - 集約に公開セッターを置かず、状態変更はドメインメソッド(`Approve()` 等)のみ。
  - 分析は**状態を持たないドメインサービス** + イミュータブルな record レポートで表す。
- これらの規約を**アーキテクチャテスト(NetArchTest)で強制**する(依存方向・命名・sealed 等)。

## 結果

- 業務ルールが Domain に集約され、永続化(SQLite)や UI(React)の変更に影響されない。
- 大規模な要件変更(ADR-0002)でも、変更範囲を層ごとに追跡できた。
- 反面、単純な CRUD にも層をまたぐ記述が必要でボイラープレートが増える。小規模機能では冗長に感じられる。
- ポート数・値オブジェクト/集約の列挙をアーキテクチャテストに固定値で持つため、構成変更時は同時更新が必要。
