E2Eテスト ガイド

総合原価管理システムの E2E テストを日本語 Gherkin(機能 / シナリオ / 前提 / もし / ならば)で書いたシナリオ 29 件(API E2E 19 件・ブラウザE2E 10 件)が、何を、どの数値で確かめているか。

API E2E
tests/e2e/api/Features/*.feature
ブラウザE2E
tests/e2e/browser/features/*.feature
ステップ定義
tests/e2e/api/Steps/・tests/e2e/browser/steps/
件数
19 件 + 10 件 = 29 件

1. このガイドについて

E2E テストは、システムを外側から操作して、部品のつながりまで含めて正しく動くことを確かめるテストです。このリポジトリには 2 種類あり、どちらもシナリオを日本語 Gherkin の .feature ファイルに書いています。.feature を読めば、何を確かめているかがコードを読まずに分かります。

件数はシナリオアウトラインを例の行ごとに数えています。API E2E には Gherkin になる前から使っている xUnit のテスト(ApiJourneyTests.cs・AuthTests.cs など)も残してあり、同じ内容を別の書き方で確かめています。

ほかのテストとの役割分担

E2Eつながりと表示

API E2E は「HTTP のつながりと数値の正しさ」、ブラウザE2E は「画面の操作と表示」を確認します。代表的な業務の流れをたどるのが役目で、ルールの細かい組み合わせまでは網羅しません。

それ以外業務ルールと画面の細部

業務ルールの細かい組み合わせは、結合テストの Gherkin シナリオ(tests/integration/backend/Application/Features/*.feature)、xUnit のテスト、プロパティベーステスト(CsCheck)が受け持ちます。画面だけの細かい振る舞い(折りたたみ・入力チェック・送るリクエストの中身・トースト)は、フロントエンド単独テスト(tests/unit/frontend。API は MSW でモック)が受け持ちます。

3. API E2E

3.1 仕組み

  • 書き方: Reqnroll(SpecFlow の後継)で .feature を xUnit のテストに変換します。ステップは「API で … する」と書き、成功(2xx)を前提にした呼び出しは期待と違う応答ならその場で失敗します。エラーを確かめるシナリオは「応答は 400 で、エラーメッセージに … を含む」で検証します。
  • 起動: APIコンテキスト が ApiFixture(WebApplicationFactory<Program>)で WebApi をテストのプロセス内でまるごと起動します。ネットワークポートは使いません。「API の認証が有効になっている」と書いたシナリオだけ、認証つきの 認証ありのApi で起動します。
  • DB: シナリオごとに一時 SQLite ファイルを作り、シナリオ終了時に削除するので、シナリオ同士が影響しません。
  • 名前と ID: フィーチャーには部・課・案件を名前で書き、API が払い出した ID への読み替えはステップ定義が受け持ちます。
  • 実行日に左右されない: 半期は "2026-H1" と明示しています。

3.2 業務フロー(APIによる業務フロー.feature)

背景で部「営業本部」・課「開発1課」・案件「PJ-A」「PJ-B」を登録してから、各シナリオを始めます。数値は 2 章の表のとおりです。

シナリオ確認すること
予算を策定して承認すると、区分合計と計画損益が応答に入る起票した予算が版 1。明細 5 件を登録した応答の区分合計(売上高 300 万・加工費 140 万・外注費 70 万・期間費用 30 万)と計画損益 60 万。承認すると状態が Approved。
実績を計上すると、予実差異と案件別損益が API で取得できる実績 5 件を計上すると、売上差異 0・コスト差異 +5 万、差異明細に案件名が出る。課全体の実績損益 55 万・実績の期間費用 32 万、案件別の実績損益(案件A 62 万・案件B 25 万)。
改定版を承認すると旧版は失効し、版の比較と差異の基準に反映される改定版が版 2 で明細 5 件を引き継ぐ。加工費を 150 万にして承認すると、版 1 が Superseded・版 2 が Approved。版の比較で加工費 +10 万、予実差異の基準が版 2 に切り替わる。
部の予実サマリを確認して部を承認し、課が改定しても承認は残り、取り消せる部の計画売上 300 万、課別内訳は承認済みの課 1 件、承認できる状態で未承認。部の承認は 204。課が改定版を承認しても部の承認は残り、取り消すと 204 で未承認に戻る。
費目マスタに費目を追加すると期間費用の明細に使えるシード済みの費目 PERSONNEL・LICENSE がある。教育研修費(TRAINING)を追加すると、期間費用の明細に 25 万で登録できる。

3.3 エラー応答(APIのエラー応答.feature)

業務エラーが、正しい HTTP ステータスと日本語メッセージで返ることを確認します。

シナリオ操作期待する応答
存在しない課を取得すると 404 になる存在しない課 ID を取得する404 「見つかりません」
明細のない予算を承認しようとすると 400 になる明細のない予算を承認する400 「承認できません」
半期の形式が "yyyy-H1" か "yyyy-H2" でなければ 400 になる(アウトライン 3 例)"2026-04"・"2026-H3"・"H1-2026" で予算を起票する400 「半期の形式が不正です」
未承認の課がある部を承認しようとすると 400 になる予算のない課がいる部を承認する400 「未承認の予算がある課」

3.4 認証(APIの認証.feature)

本番では Amazon Cognito が発行したアクセストークンだけを受け付けます。テストでは Cognito の代わりに、テスト用の鍵で署名した同じ形のトークンを使います。

トークン応答
正しいアクセストークン200
トークンなし / 別のアプリクライアントに発行されたトークン / ID トークン / 期限切れ / 発行者が違う / 署名鍵が違う401

このほか、開発環境以外で認証の設定(Auth:Authority)がなければ API が起動しないことを確かめます。

4. ブラウザE2E

4.1 仕組み

  • 書き方: playwright-bdd で .feature から Playwright のテストを生成します(npx bddgen。npm test は生成してから実行します)。tests/e2e/browser は独立した npm パッケージで、画面は frontend の Vite 開発サーバを起動して使います。生成先の .features-gen/ は gitignore 済みです。
  • 前提は API、操作と検証は画面: 「前提 部 … に課 … がある」「課 … の今期の予算が次の明細で承認されている」などの準備は、画面を通さずに API で行います。「もし」「ならば」だけを画面で操作・確認するので、シナリオが短く、互いに独立します。部と課の登録そのものは「計画策定」の最初のシナリオで画面から確かめています。
  • 起動: tests/e2e/browser/playwright.config.ts の webServer で、バックエンド(dotnet run、ポート 5100)とフロントエンド(Vite、ポート 5173)を自動で起動します。
  • DB とデータの衝突回避: 実行 1 回ごとに一時 SQLite を 1 つ使い、全シナリオで共有します。部・課の名前と費目コードにはシナリオ固有の接尾辞を付けるので(フィクスチャ 業務データ)、並列に実行しても、同じ DB で再実行しても重複しません。
  • 半期: 画面の初期半期は実行日で決まります(4〜9 月は上期、10〜3 月は下期)。API で準備する予算・実績も同じ規則で「今期」に作ります。
  • 要素の見つけ方: ラベル(getByLabel)やボタン名(getByRole)など、利用者に見える名前で探します。

4.2 計画策定(計画策定.feature)

シナリオ確認すること
部と課を画面から登録し、一覧から辿れるトップ画面で部を登録すると一覧に出て、部の画面で課を登録すると一覧に出て、課の画面まで辿れる。
予算編集画面で案件を追加して金額を入力し、承認できる予算編集画面の中で案件 A・B を追加し、案件 × 区分のセルに金額を入れる(セルから離れると自動保存)。案件A の粗利率 30.0%。人件費 30 万を入れると売上高 ¥3,000,000 と計画損益 ¥600,000 が出る。承認すると「承認済」。
承認した課の予算が部の画面に集計され、部予算を承認・取り消しできる部の画面に粗利率 20.0% と、課ごとの予算比較(300 万・60 万)が出る。予実サマリタブに課別の内訳が出る。部予算を承認すると「承認済」、取り消すと「未承認」。

4.3 実績と分析(実績と分析.feature)

背景で 2 章の予算を API で承認しておきます。

シナリオ確認すること
区分ごとに案件別・費目別の実績を計上できる実績入力画面で区分・案件(期間費用なら費目)・金額を選んで 5 件計上し、一覧に金額が出る。計上が終わると金額欄が空になるので、次の計上に進む前にそれを待つ(連続送信の競合対策)。
区分別の予実差異と案件別の損益が表示される実績を API で計上しておき、予実差異タブでコスト予算 ¥2,400,000・差異 ¥+50,000・加工費明細の「案件A」を確認する。損益タブで案件A と「期間費用(課共通)」の行、案件A の実績損益 ¥620,000、課全体の実績 ¥550,000 を確認する。
改定版を承認すると旧版は失効し、版の比較で増減を確認できる「上期見直し」のドラフトで案件A の加工費を 150 万に変えて承認すると、予算バージョン一覧に「失効」バッジが出る。予算バージョン比較で加工費の増減 ¥+100,000。

4.4 予算明細の入力(予算明細の入力.feature)

背景で課を API で用意し、画面で「当初予算」のドラフトを作っておきます。入力が API を通して保存され、サーバが計算した合計が画面に戻ることを確かめます。

シナリオ確認すること
明細を月ごとに入力すると半期合計に反映される月次入力ダイアログで 1 か月目 100 万・2 か月目 50 万を入れると、半期合計 ¥1,500,000 が自動計算される。保存後、行に月次バッジが付き、売上高タイルも 150 万。
費目を明細名で細分すると、費目の小計と期間費用は明細の合計になるライセンス費に明細 AWS 30 万・GitHub 20 万を追加すると、小計と期間費用タイルが 50 万。

月次入力が実行日に左右されない理由: 画面の初期半期は実行日で決まるため、月次の入力欄は「4月」などの月名ではなく、半期内の位置(1 か月目・2 か月目)で指定しています。

フロントエンド単独テストに移した検証: 明細の折りたたみ・展開、明細名の変更と削除、費目一括から明細への切り替え(費目一括の削除→明細の登録の順序まで)、エラーのトーストは、tests/unit/frontend/pages/予算編集画面/ で確かめています。「別の課なら同じ案件コードを使える」は業務ルールなので、結合テストの Gherkin「組織と案件と費目のマスタ」で確かめています。

4.5 マスタ管理(マスタ管理.feature)

シナリオ確認すること
費目マスタ画面で追加した費目が予算編集の期間費用に現れる費目マスタ画面で追加した費目(旅費交通費)が、課の予算編集の期間費用に出る。予算編集画面には費目を追加するフォームがない。
登録済みの案件のコードと名称を後から変更できるPJE-1「編集前案件」→ PJE-2「編集後案件」に変更でき、エラーが出ない。

5. 読み方と注意点

シナリオは互いに独立している: ブラウザE2E のシナリオはそれぞれ必要なデータを自分で用意するので、どれか 1 件が失敗しても、ほかのシナリオが巻き込まれて失敗することはありません。失敗したシナリオの .feature と Playwright のトレースを見て原因を調べます。

ステップを足す前に既存のステップを探す: 言い回しの揺れでステップを増やすと、同じ操作のステップ定義が散らばります。npx bddgen(ブラウザ)やテスト実行(Reqnroll)は、定義のないステップがあるとそのシナリオを失敗・未実行にするので、全件が実行されたことを確かめてください。

E2E では確認していないこと(ほかのテストで確認済み)

確認していない範囲内容どこで確認しているか
ブラウザE2E実績の削除Application 層のテスト、フロントエンド単独「実績入力画面」
ブラウザE2E入力チェック(明細名・金額が空、明細名を空にしての変更)とエラーのトーストフロントエンド単独「予算編集画面」「実績入力画面」「トースト」
ブラウザE2E計画にない明細名の実績(予定外)の表示Gherkin「予実差異と損益」(Application 層)
ブラウザE2E部承認ができないときのエラー表示API E2E、Gherkin「部の予実と承認」(Application 層)
API E2E月次入力・期間費用の明細名Gherkin「課予算の策定と改定」(Application 層)、ブラウザE2E「予算明細の入力」

6. 実行方法

API E2E

cd backend
dotnet test ../tests/e2e/api

ブラウザE2E

(cd frontend && npm ci)           # 画面の開発サーバ用(初回のみ)
cd tests/e2e/browser
npm ci                            # 初回のみ
npx playwright install chromium   # 初回のみ
npm test                          # bddgen で .feature からテストを生成して実行

# Claude のリモート環境では同梱の Chromium を使う
CI= PW_CHROMIUM=/opt/pw-browsers/chromium npm test
