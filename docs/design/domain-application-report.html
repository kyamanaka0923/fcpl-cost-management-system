1. このレポートについて

本書は、総合原価管理システムのバックエンドのうち ドメイン層 と アプリケーション層 の ソースコードを、レビュー担当者が上から順に読めるようまとめたものです。 クラスを機械的に列挙するのではなく、ドメイン駆動設計の戦術パターン (値オブジェクト / 集約・エンティティ / ドメインサービス / ポート / アプリケーションサービス)ごとに整理し、 それぞれが担う不変条件と、どこで検証されているかを明示しています。

この業務ドメインの前提(先に押さえると読みやすい)

  • 組織は 部(Division)> 課(Department) の 2 階層。予算・実績を持つのは課だけで、部は配下課の合計を見る集計ビュー。
  • 管理単位は 課 × 半期(yyyy-H1 / yyyy-H2)。この 1 組に対して予算がバージョン管理される。
  • 予算は 売上高・加工費・外注費・期間費用 の 4 区分を 1 つの集約でまとめて承認する。
  • 明細は金額のみ(数量×単価は扱わない)。金額は「半期一括」または「月次(半期内 1〜6 月目)」で入力する。
  • 売上高・加工費・外注費は案件別、期間費用は費目別(さらに費目内を自由入力の明細名で細分できる)。

本書での記号

集約ルート 一貫性の境界。外部からは ID で参照する 値オブジェクト readonly record struct。等価性は値で決まる ドメインサービス ステートレス。集約に属さない計算 ポート ドメイン層に置いた interface。実装はインフラ層 アプリケーションサービス ユースケースの調停役

2. レイヤと依存方向

依存は常に外側から内側(ドメイン)へ向きます。ドメイン層は .csproj の時点で 他プロジェクトへの参照を 1 つも持ちません。アプリケーション層はドメイン層だけを参照します。 インフラ層と Web API 層はどちらも内側を参照する側にあり、内側からは見えません。

CostManagement.WebApi(入力アダプタ)

Minimal API のエンドポイント。例外変換: DomainException → 400 / NotFoundException → 404。

▼ 呼び出す

CostManagement.Application(ユースケース = 入力ポート)

8 つのアプリケーションサービス + DTO 群 + ISystemClock / NotFoundException。 トランザクション的な手順、複数集約にまたがる検証、名称解決、DTO 変換を担う。

▼ 参照する(ProjectReference は Domain のみ)

CostManagement.Domain(モデルの中心)

7 集約 + 4 ドメインサービス + 値オブジェクト + 7 つの永続化ポート。外部参照ゼロ。

▲ ポートを実装する(出力アダプタ)

CostManagement.Infrastructure(出力アダプタ)

SQLite + Dapper のリポジトリ実装、SystemClock、DI 登録(AddCostManagement)。

DI 登録はインフラ層の DependencyInjection.AddCostManagement に集約されており、 リポジトリ 7 種・ISystemClock・ドメインサービス 4 種・アプリケーションサービス 8 種を すべて Singleton として登録します。ドメインサービスとアプリケーションサービスがいずれも 状態を持たない(フィールドは依存だけ)ため、Singleton で安全です。

4. 値オブジェクトと共有カーネル

Domain/Shared は全集約が共有する共有カーネルです。 値オブジェクトはすべて readonly record struct で定義され、 不変・値等価・コンストラクタでの検証という 3 点が揃っています(この規約はアーキテクチャテストで強制されています)。

4.1 Money — 金額

readonly record struct Money(decimal Value)金額(円)

金額計算を decimal の裸の値ではなく型で包むだけの薄い値オブジェクトです。 演算子 + / - / *(スカラー倍)と IComparable<Money> を実装し、 Zero を集計の初期値として公開します。IsNegative は「金額は 0 以上」という 入力検証の共通述語として、集約側から繰り返し使われます。 

public static Money operator +(Money a, Money b) => new(a.Value + b.Value);
public bool IsNegative => Value < 0m;
public override string ToString() => Value.ToString("#,0.##");   // 3桁区切り

出典: Domain/Shared/Money.cs

読みどころ: 通貨単位や丸めのルールは持っていません(円・端数なしの前提)。 また分析サービスのレポートは Money ではなく素の decimal を返す設計で、 集約の内部は Money、レポート/DTO 境界からは decimal という線引きになっています。

4.2 FiscalHalf / HalfTerm — 会計半期

readonly record struct FiscalHalf年度 + 上期/下期

本システムの時間軸そのものです。Year(2000〜2100)と HalfTerm(H1 = 4〜9 月 / H2 = 10〜3 月)を持ち、 "yyyy-H1" / "yyyy-H2" の文字列と相互変換します。 DB 保存も API 表現もこの文字列形式で統一されており、境界を越えるときは必ず Parse / ToString を通ります。

メンバ役割不正時
FiscalHalf(int, HalfTerm)年度と区分から生成年度が 2000〜2100 外 / 区分が H1・H2 以外 → DomainException
Parse(string)文字列から復元(境界の入口)形式不正 → DomainException「半期の形式が不正です」
CompareTo と < <= > >=Year * 2 + (int)Half による時系列順の比較—
ToString()$"{Year:D4}-H{(int)Half}"—

4.3 型付きID — 集約間参照の唯一の手段

集約は互いにオブジェクト参照を持たず、必ず型付き ID で参照します(例: Department は Division ではなく DivisionId を持つ)。 5 つの ID はいずれも同じ形をしており、New() で GUID を採番し、ToString() で GUID 文字列を返します。 Guid の生値を使わないことで、引数の取り違え(課 ID を案件 ID に渡す等)がコンパイル時に落ちます。

型指すもの参照している側
DivisionId部Department、DivisionBudgetApproval
DepartmentId課Project、DepartmentBudget、ActualEntry
ProjectId案件BudgetLine、ActualEntry
DepartmentBudgetId課予算(バージョン単位)—(外部から指定されるのみ)
ActualEntryId実績 1 件—

設計判断: 案件は コードではなく ProjectId(GUID)で参照されます。 これにより案件コードを後から変更しても予算明細・実績の参照が壊れません(5.4 参照)。 一方、費目は CostElementCode(文字列)で参照されており、こちらはコード自体が同一性を担います。

4.4 CostElementCode — 費目コード

readonly record struct CostElementCode期間費用の費目コード

型付き ID と違い、コンストラクタで正規化(trim + 大文字化)まで行うのが特徴です。 "license" と " LICENSE " は同じ値になり、record struct の値等価によって 辞書キー・比較にそのまま使えます。空文字は DomainException(「費目コードは必須です。」)。 

public CostElementCode(string value)
{
    if (string.IsNullOrWhiteSpace(value))
        throw new DomainException("費目コードは必須です。");
    Value = value.Trim().ToUpperInvariant();
}

4.5 列挙と仕様ヘルパ

Budgeting/DepartmentBudget.cs の冒頭には、集約本体の前に「この業務の語彙」が定義されています。 とくに BudgetCategories.ValidateKey は予算明細と実績の両方から呼ばれる唯一の仕様であり、 明細キーの整合性がモデル全体で一貫する要になっています。

enum BudgetStatus予算の状態
  • Draft — 策定中。明細を編集できる唯一の状態
  • Approved — 承認済み。予実比較の基準になる
  • Superseded — 後続版の承認で失効。履歴として残る
enum BudgetCategory4 区分
  • Revenue 売上高(案件別)
  • Processing 加工費(案件別)
  • Outsourcing 外注費(案件別)
  • PeriodCost 期間費用(費目別・課共通)
static class BudgetCategories区分と明細キーの仕様

IsProjectBased() は「案件別に明細を持つ区分か」を判定する拡張メソッドで、区分の分岐がコード中に散らばるのを防いでいます。ValidateKey は次の排他を強制します。

区分ProjectIdElementCode違反時のメッセージ
Revenue / Processing / Outsourcing必須指定不可「売上高・加工費・外注費の明細には案件を指定してください。」ほか
PeriodCost指定不可必須「期間費用の明細には費目を指定してください。」ほか
上記以外(将来の追加漏れ)—「予算区分が不正です: {category}」

最後の else 節がある点が重要です。区分を増やしたのに分類を決め忘れた場合、 暗黙に通過せず即座に例外になります。

static class HalfMonths半期内の月インデックス

Count = 6 と Validate(int month) のみ。月は暦月ではなく半期内の 1〜6 番目で表され、 H1 の 1 は 4 月、H2 の 1 は 10 月に相当します。BudgetLine(月次入力)と ActualEntry(計上月)の両方から使われます。

4.6 DomainException

不変条件違反を表す唯一の例外型です(sealed)。メッセージはそのまま利用者に見せられる日本語で書く規約で、 Web API 層がこれを HTTP 400 に変換します。一方「対象が見つからない」はドメインの不変条件ではないため、 アプリケーション層の NotFoundException(→ 404)と明確に役割が分かれています。

全集約に共通する 4 つの書き方の約束

  1. クラスは sealed、private コンストラクタ。
  2. 生成は静的ファクトリ(Create / Record / CreateInitial …)。ここで検証する。
  3. 永続化からの復元は Restore(...)。検証をスキップして状態を再構築する(DB にある = 過去に検証済み、という前提)。
  4. 公開セッターを置かない。状態変更はドメインメソッド(Rename / Approve / Upsert…)だけ。

課の上位組織。予算を策定しません。持つのは Id / Code / Name / CreatedAt のみで、配下課への参照も持ちません(参照は Department 側から DivisionId で張られます)。

5.5 CostElement(費目) 集約ルート

5.6 DepartmentBudget(課予算) 集約ルート — 中核

本システムでもっとも情報量の多い集約です。(課, 半期) ごとにバージョン管理された 1 つの予算で、 4 区分すべての明細を内部に抱え、まとめて 1 回で承認されます。以下、5 つの観点に分けて読み解きます。

ヘッダに金額フィールドが 1 つも無いことが設計の要です。区分合計は常に明細から導出されます。

public Money CategoryTotal(BudgetCategory category) =>
    _lines.Where(l => l.Category == category)
          .Aggregate(Money.Zero, (sum, l) => sum + l.Amount);

public Money TotalCost => CategoryTotal(Processing) + CategoryTotal(Outsourcing) + CategoryTotal(PeriodCost);
public Money PlannedProfit => CategoryTotal(Revenue) - TotalCost;

不変条件: 「月次モードなら Amount = MonthlyAmounts の合計」は SetMonthly が計算して代入する形で構造的に保証されています (外から Amount を書ける経路が存在しない)。

出典: Domain/Budgeting/DepartmentBudget.cs(BudgetLine 部)

(d) 明細キーと期間費用の「モード一貫性」

区分明細の一意キー操作メソッド
売上高 / 加工費 / 外注費(区分, ProjectId)UpsertProjectLine / UpsertProjectLineMonthly / RemoveProjectLine
期間費用(期間費用, ElementCode, PeriodDetail)UpsertPeriodCostLine / UpsertPeriodCostLineMonthly / RemovePeriodCostLine / RenamePeriodCostDetail

すべて Upsert(同一キーなら上書き、無ければ追加)で、同じキーの明細が 2 行できることはありません。 期間費用にはさらに 1 段の制約があります。EnsurePeriodModeConsistent は、 同じ費目の中で「費目一括(明細名なし)」と「明細(明細名あり)」が混ざることを禁じます。 

if (detail is null && elementLines.Any(l => l.PeriodDetail is not null))
    throw new DomainException("この費目には明細があります。費目一括の金額ではなく明細で入力してください。");
if (detail is not null && elementLines.Any(l => l.PeriodDetail is null))
    throw new DomainException("この費目は費目一括で入力されています。明細を使うには先に費目一括の金額を削除してください。");

理由は二重計上の防止です。「ライセンス費 500 万」と「ライセンス費 / AWS 300 万」が併存すると、 CategoryTotal は単純合計なので 800 万になってしまいます。混在を禁じることで 「費目合計 = 明細の合計」がそのまま成り立ちます。

(e) 明細名の改名 と 復元

メソッドふるまい
RenamePeriodCostDetail(elementCode, oldDetail, newDetail) ドラフトのみ。対象が無ければ例外。新旧が同じなら何もせず return。同一費目内に同名があれば「同じ費目に同じ明細名が既に存在します。」。空への改名は不可(= 費目一括へは戻せない)。金額・月次・明細 ID は保持される
Restore(id, departmentId, fiscalHalf, version, label, status, createdAt, approvedAt, lines) タプル列から明細を再構成。Monthly が空なら半期一括、非空なら月次として復元。区分・費目コードは文字列からパースされ、キーの排他検証はここでも走る

意図された非対称: 改名は予算側だけに効きます。実績(ActualEntry)は明細名を 文字列で疎結合に持つため追随せず、旧名で計上済みの実績は分析上「予定外(IsUnplanned)」として現れます。 これは仕様として文書化された挙動で、レビュー時に「バグに見えるが仕様」と認識しておくべき箇所です。

5.7 ActualEntry(実績) 集約ルート

予算明細と同じ軸((課, 半期, 区分, 案件 or 費目 × 明細名))で計上される実績 1 件。 予算と違い、同一キーに何件でも計上でき、分析時に合算されます(月次の実績を 6 回に分けて入れる、都度計上する、といった運用に対応)。 生成後は完全にイミュータブルで、更新手段はありません(訂正は削除 + 再計上)。

プロパティ説明
DepartmentId / FiscalHalf / Category計上先の管理単位と区分
ProjectId? / ElementCode?予算明細と同じ排他ルール
PeriodDetail期間費用の明細名(任意)。計画に無い名前でも計上できる
Month半期内の 1〜6。null = 半期一括の計上
Amount / Note / RecordedAt金額(0 以上)/ 備考(trim、空なら null)/ 計上日時(UTC)

Record(...) が行う検証は 4 つです。

  1. BudgetCategories.ValidateKey — 予算明細とまったく同じ仕様を共有
  2. HalfMonths.Validate — 月を指定した場合のみ
  3. 金額 ≧ 0
  4. 明細名は期間費用のときだけ(BudgetLine.NormalizeDetail で正規化してから判定)

出典: Domain/Actuals/ActualEntry.cs

注目点: 実績は「対応する予算明細が存在するか」を検証しません。 予算と実績を疎結合に保ち、計画外の支出もそのまま記録できるようにする設計で、 その差は分析時に IsUnplanned フラグとして表面化します。 また Month は入力の粒度にすぎず、集計・差異分析はすべて半期粒度で行われます。

5.8 DivisionBudgetApproval(部予算承認) 集約ルート

(部, 半期) ごとに 1 件だけ存在しうる承認レコードで、レコードの存在そのものが「承認済み」を意味します (状態フラグを持たない)。取り消しは削除です。 課の承認フロー(DepartmentBudget.Approve)とは完全に独立しており、 部承認後に課が予算を改定しても部承認は残ります。

集約自身は「承認してよいか」を判断しません — Approve(divisionId, fiscalHalf, now) は ただレコードを作るだけです。「配下の全課が承認済み予算を持つか」という条件は複数集約の横断的な問い合わせが必要なため、 DivisionBudgetApprovalService(アプリケーション層)の責務として明示的に切り出されています。

出典: Domain/Divisions/DivisionBudgetApproval.cs

6. ドメインサービス

分析ロジックはどの集約にも属さない(複数集約を入力に取る)ため、4 つのステートレスなドメインサービスに切り出されています。 いずれも依存フィールドを持たず、入力を受け取ってイミュータブルな record のレポートを返すだけの純関数的な構造です (だから DI で Singleton にできる)。レポートは Money ではなく decimal を公開します。

サービス入力出力役割
BudgetVarianceAnalysisServiceDepartmentBudget + ActualEntry 群VarianceReport予実差異
BudgetComparisonServiceDepartmentBudget × 2BudgetComparisonReportバージョン間比較
ProfitAnalysisServiceVarianceReportProfitReport案件別・全体の損益
DivisionBudgetSummaryServiceDepartmentVarianceInput 群DivisionSummaryReport部の合計

4 つは直列に積み上がる関係です: 差異分析 → (損益分析 | 部集計)。損益も部集計も、生の実績ではなく差異分析の結果を入力に取るため、 「どの階層で見ても数字が一致する」ことが構造的に保証されます。

6.1 BudgetVarianceAnalysisService — 予実差異分析

アルゴリズムは 4 ステップです。

  1. 予算を辞書化: キー = (Category, ProjectId?, ElementCode?, PeriodDetail) → 金額。集約側の一意性保証があるため ToDictionary で衝突しません。
  2. 実績を同じキーで GroupBy して合算。同一キーの複数計上がここで 1 行にまとまります。
  3. 両者のキーの和集合を取り、区分 → 費目 → 明細名 → 案件 の順に整列。予算にしか無いキーは実績 0、実績にしか無いキーは IsUnplanned = true。
  4. 4 区分ぶんのサブトータルを作り(明細が 0 件の区分も必ず 1 要素として現れる)、売上高と「それ以外の合計 = コスト」に畳んで VarianceReport を返す。

差異の符号

差異は一貫して 実績 − 予算 です。有利/不利の解釈だけが区分で反転します。

Variance > 0(実績超過)Variance < 0(実績未達)
売上高有利 IsFavorable不利 IsAdverse
加工費 / 外注費 / 期間費用不利 IsAdverse有利 IsFavorable

差異が 0 のときは IsFavorable / IsAdverse がともに false になります(排他かつ全域ではない、3 値の表現)。 なお価格差異・数量差異への分解は存在しません — 明細が金額のみだからです。

出典: Domain/Analysis/BudgetVarianceAnalysisService.cs

6.2 BudgetComparisonService — バージョン間比較

同じファイルに同居する 2 つ目のサービス。差異分析とほぼ同型のアルゴリズムで、 「実績 vs 予算」の代わりに「基準版 vs 対象版」を突き合わせ、Difference = Target − Base を出します。 冒頭で比較対象が同一の課・半期であることを検証し、違えば 「同一の課・半期の予算同士のみ比較できます。」で弾きます — このサービス唯一のガードです。

片方にしか無いキーは、もう一方が 0 として扱われます(新規追加された明細 / 削除された明細がそのまま増減として表れる)。

6.3 ProfitAnalysisService — 損益分析

VarianceReport を入力に、案件別と課全体の 2 つの損益を出します。ここは定義が 2 種類あるので読み違えやすい箇所です。

粒度損益の定義期間費用の扱い
案件別 ProjectProfitLine売上高 − 加工費 − 外注費含めない(課共通のため案件に配賦しない)
課全体 ProfitReport売上高 −(加工費 + 外注費 + 期間費用)含める

したがって 「案件別損益の合計 − 期間費用 = 全体の損益」 が成り立ちます(この整合性はテストで担保されています)。 案件別は IsProjectBased() の区分の明細だけを ProjectId で GroupBy して構成します (期間費用の明細は ProjectId が null なので、この時点で自然に除外される)。

粗利率は 損益 ÷ 売上高 で、売上高が 0 のときは null(0 除算を避け、「率が定義できない」ことを型で表現)。

出典: Domain/Analysis/ProfitAnalysisService.cs

6.4 DivisionBudgetSummaryService — 部集計

課ごとの VarianceReport のリスト(DepartmentVarianceInput)を受け取り、単純に足し合わせます。 出力は「区分別の部合計」「部全体の売上・コスト・損益の予実」「課別内訳」の 3 点セットで、 「部合計 = 課別内訳の合計」が定義上必ず成立します(同じ入力から両方を作っているため)。

このサービス自体はリポジトリを知らないため、「承認済み予算がある課だけを入力に含める」判断は呼び出し側 (AnalysisService)が行います。未策定の課を 0 として混ぜてしまうか、そもそも入力から外すかで 部の数字の意味が変わるため、ここは責務の切れ目として意識して読む価値があります。

出典: Domain/Analysis/DivisionBudgetSummaryService.cs

7. ポート(リポジトリ)

永続化の抽象はドメイン層に interface として置かれ(依存性逆転)、実装はインフラ層にのみ存在します。 現在 7 つで、この数はアーキテクチャテストに固定値で書かれており、集約を増減したら同時に更新する運用です。 全メソッドが CancellationToken ct = default を受け、命名は Find…(見つからなければ null)/ List… / Add / Update / Delete に統一されています。

ポート主なメソッド特記事項
IDivisionRepositoryFindById / FindByCode / List / Add / Update部コードは全体で一意
IDepartmentRepositoryFindById / FindByCode / ListByDivision / Add / UpdateFindByCode が部でスコープされていない(= 課コードは全社一意の扱い)
IProjectRepositoryFindById / FindByCode(departmentId, code) / ListByDepartment / Add / Updateコード検索が課でスコープされる。DB 側も UNIQUE (department_id, code)
ICostElementRepositoryFindByCode / List / Add更新・削除は未提供
IDepartmentBudgetRepositoryFindById / List(dept, half) / FindLatestApproved / GetMaxVersion / Add / UpdateUpdate は「ヘッダ更新 + 明細の洗い替え」。GetMaxVersion は改定版の採番用(無ければ 0)
IActualEntryRepositoryFindById / List(dept, half) / Add / Delete更新は無い(訂正は削除 + 再計上)
IDivisionBudgetApprovalRepositoryFind(div, half) / Add / Delete(div, half)承認状態 = レコードの有無

ポートの粒度について: クエリはすべて「集約を返す」形に閉じており、 プロジェクション用の読み取り専用クエリ(CQRS の Read Model)は存在しません。 そのぶん AnalysisService は集約をメモリに読み込んでから集計します。 現在のデータ規模では素直で追いやすい選択ですが、部配下の課が増えると 12 章で触れる N+1 の形が効いてきます。

8. アプリケーション層

8.1 共通の構造

アプリケーションサービスは薄い調停役に徹しています。8 クラスすべてが同じ骨格です。

  1. 依存はコンストラクタ注入のみ。readonly フィールドで保持し、状態は持たない。
  2. 入口で生値を VO へ変換: new DepartmentId(guid)、FiscalHalf.Parse(str)、ParseCategory(str)。ここで形式不正は DomainException になる。
  3. 存在確認: Find…Async(...) ?? throw new NotFoundException(...) のパターン。RequireAsync という private ヘルパに畳まれていることが多い。
  4. 複数集約にまたがる検証: コード重複、案件の課所属、部配下の全課が承認済みか、など。
  5. 集約のドメインメソッドを呼ぶ。ここでドメイン固有の不変条件が守られる。
  6. リポジトリに保存し、DTO へ変換して返す(internal static ToDto / ToDetailDto)。
ISystemClock時刻ポート

UtcNow だけを持つインターフェース。集約のファクトリは DateTime now を引数で受け取る設計なので、 「今」を知っているのはアプリケーション層だけです。ドメインは時刻の取得手段に依存せず、テストでは固定時刻を注入できます。 本番実装 SystemClock はインフラ層にあります。

NotFoundException未検出

「不変条件違反(DomainException → 400)」と「対象が無い(NotFoundException → 404)」を 層で分けています。ドメイン層はこの例外を知りません — 存在確認はアプリケーション層の仕事だからです。

「なぜこの検証がここにあるのか」を一望できるようにまとめます。判断基準は明快で、1 つの集約の内部で完結する規則はドメイン、複数の集約やリポジトリの問い合わせを要する規則はアプリケーションです。

11. 主要シナリオの流れ

11.1 予算の策定 → 承認 → 改定

  1. DepartmentBudgetService.CreateDraftAsync: 課と半期を指定してドラフト起票。初回は CreateInitial で v1、明細ゼロ。
  2. UpsertLineAsync を明細の数だけ呼ぶ。案件別は案件の課所属を、期間費用は費目マスタの存在を検証してから集約に反映し、その都度 UpdateAsync(ヘッダ + 明細の洗い替え)で保存。
  3. ApproveAsync: 集約が Draft かつ明細 ≧ 1 件を確認して Approved に。続いて同一 (課, 半期) の旧承認版を Supersede() して保存。
  4. 期中に見直しが必要になったら CreateDraftAsync(BaseBudgetId 省略なら最新の非ドラフト版が基準)。明細が新しい ID で複製された v2 ドラフトができる。
  5. v2 を承認すると v1 が Superseded になり、履歴として残る。CompareBudgetsAsync(1, 2) で増減を明細単位に見られる。

11.2 実績計上 → 差異分析 → 損益

  1. ActualEntryService.RecordAsync: (課, 半期, 区分, 案件 or 費目 [, 明細名] [, 月]) と金額で計上。予算明細との突合はしない。
  2. AnalysisService.AnalyzeVarianceAsync: 基準予算(既定は最新承認済み)と当該半期の実績を全件取得。
  3. BudgetVarianceAnalysisService.Analyze: 実績を同一キーで合算し、予算キーとの和集合で明細ごとの差異を算出。予算に無いキーは IsUnplanned。
  4. アプリケーション層が案件名・費目名を解決し、IsFavorable / IsAdverse を展開して VarianceReportDto に。
  5. GetProfitSummaryAsync は同じ VarianceReport を ProfitAnalysisService に流し、案件別損益(期間費用を除く)と課全体の損益・粗利率を得る。

11.3 部の集計と部承認

  1. AnalysisService.GetDivisionBudgetSummaryAsync: 配下課をコード順に列挙し、課ごとに最新承認済み予算 + 実績で差異分析。
  2. 承認済み予算が無い課は合計から除外し、課別内訳にだけ HasApprovedBudget = false の行として残す。
  3. DivisionBudgetSummaryService.Summarize が区分別・全体・課別内訳を合計する。
  4. 同じ応答に部承認の状態(IsApproved / ApprovedAt)と CanApprove を載せる。
  5. DivisionBudgetApprovalService.ApproveAsync は全課の承認済み予算を再確認したうえで承認レコードを作る。取り消しは RevokeAsync(冪等)。

12. レビュー時の着眼点

以下はコードを読んで気づいた点の整理です。不具合の指摘ではなく、仕様として意図されているかを 確認したい箇所、および将来の変更時に影響が出やすい箇所です。

#箇所観察確認したいこと
1 DepartmentService.CreateAsync 課コードの重複判定が FindByCodeAsync(code) で、部でスコープされていない(= 全社一意)。案件コードは課ごとに一意という非対称がある 課コードは全社一意で正しいか(部が違えば同じ課コードを使いたい運用が無いか)
2 DepartmentBudgetService.ApproveAsync 承認 → 旧版の失効 → 保存 が複数回のリポジトリ呼び出しに分かれており、トランザクション境界が無い。途中で失敗すると「承認済みが 2 つ」の状態が残りうる 単一プロセス・SQLite の前提で許容する判断か。将来 Unit of Work を導入する余地
3 AnalysisService.GetDivisionBudgetSummaryAsync 配下課の数だけ「最新承認済み予算」「実績一覧」を順次取得する(N+1)。課が増えるほど線形に遅くなる 想定される課の規模。必要なら一括取得のポート追加を検討
4 Division.Rename / Department.Rename ドメインメソッドとリポジトリの UpdateAsync は用意されているが、アプリケーション層から呼ぶユースケースが存在しない(案件だけ UpdateAsync がある) 部名・課名の変更は今後提供する予定か。当面不要なら未使用であることを認識しておく
5 DepartmentBudgetService.ParseCategory Enum.TryParse(..., ignoreCase: false, ...) のため、区分文字列は "Revenue" のような大文字小文字完全一致が必要 API のクライアント側と表記が揃っているか(意図的な厳格さと読める)
6 DivisionBudgetApprovalService.ApproveAsync 再承認時に「削除 → 追加」で ApprovedAt を更新している。承認 ID は毎回変わる 承認履歴を残す要件が将来出てこないか(現状は最新 1 件のみ)
7 BudgetLine.RemovePeriodCostLine 明細名を省略すると「費目一括の行」だけが削除対象になる(その費目の明細を一括削除する操作ではない) UI 側の「費目ごと削除」操作がある場合、明細を 1 件ずつ削除する実装になっているか
8 UpsertBudgetLineRequest.MonthlyAmounts 空の辞書は null ではないため月次側の分岐に入るが、SetMonthly が保持する月別金額を 0 件にするため、結果は金額 0 円の半期一括明細(IsMonthly = false)になる。Amount に何を入れて送っても無視される 「明細を残したまま金額を空にする」意図の入力がここに流れ込まないか(金額 0 の明細が残る)
9 ProfitAnalysisService GroupBy(l => l.ProjectId!.Value) と null 免除演算子を使っている。案件別区分の明細は必ず案件 ID を持つ、という ValidateKey の保証に依存している 区分を追加する際は IsProjectBased と ValidateKey の整合を必ず同時に見直す
10 NameLookup.ProjectCode / ProjectName 見つからないときの既定値が空文字と null で非対称 フロント側の表示要件に合わせた意図的な差か
11 集約の Restore 基本は検証をスキップするが、BudgetLine だけは internal コンストラクタ経由で ValidateKey が走る。DB に不整合レコードがあると読み出し時に DomainException になる スキーマ移行時のデータ整合(意図的な安全弁と読める)
12 ドメインサービス 4 種の AllCategories 4 区分の配列が 3 ファイルに重複定義されている 区分を追加・削除するときの更新漏れに注意(共通化の余地)

まとめ

このコードベースの読みやすさは、「不変条件を検証で守る」より「壊せない構造にする」を優先している点に由来します。 区分合計をフィールドとして持たない、月次合計を代入でしか作らせない、明細の生成経路を internal に閉じる、 承認済みなら編集メソッドが全部その場で止まる — いずれも「間違った状態を作れる経路自体を消す」設計です。 一方で、複数集約にまたがる規則は意図的にアプリケーション層へ追い出されており (ドラフト 1 件・承認済み 1 件・部承認の可否・コード一意性)、 レビューではこの境界線を意識して、どちらの層を読むべきかを切り分けるのが近道です。
