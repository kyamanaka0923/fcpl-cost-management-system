# 要件定義書 — 総合原価管理システム(予実管理)

- **対象システム**: 総合原価管理システム(課別・半期の予算策定/実績計上/差異・損益分析)
- **版**: 1.0(2026-07-18 JST 時点の実装に整合)
- **関連文書**: 概要は [README.md](../README.md)、操作は [MANUAL.md](MANUAL.md)、設計(図)は [DESIGN.md](DESIGN.md)、
  設計判断は [アーキテクチャ決定記録(ADR)](adr/README.md)、要件変更の経緯は [requests/](requests/)

本書は「システムが何を満たすべきか」を機能要件・非機能要件・アーキテクチャ制約として定義する。
本書と実装が食い違った場合は、実装または本書のいずれかに欠陥があるとみなし、
どちらかを是正する(推測で辻褄合わせをしない)。

---

## 1. 目的とスコープ

### 1.1 目的

受託開発を行う組織において、**課(部門)単位**で半期(年度の上期/下期)の原価予算を策定・承認し、
実績を計上して、**予実の差異と損益**を可視化する。金額ベースでの計画・実績管理により、
どの課・どの案件の採算が良い/悪いかを経営・現場の双方が把握できるようにする。

### 1.2 スコープ(対象)

- 組織(部・課)、案件、費目のマスタ管理
- 課 × 半期の予算策定(4区分)、バージョン管理、課承認・部承認
- 実績の計上
- 差異分析・損益分析・予算バージョン比較・部集計

### 1.3 スコープ外(非対象)

- 認証・認可・ユーザー管理(将来対応の候補。現状は未実装)
- 会計システム・勤怠/工数管理との外部連携(将来連携の候補。現状は未実装)
- 数量 × 単価による積算、価格差異/数量差異の分解(**意図的に採用しない**。ADR-0003)
- 月次を最終的な集計・損益の粒度とすること(月次は入力の内訳にとどめる。ADR-0009)

### 1.4 想定利用者

| 利用者 | 役割 |
|---|---|
| 原価管理者(課) | 課の半期予算の策定・改定・承認、実績の計上、差異・損益の分析 |
| 部門長(部) | 配下課の予算・予実の比較参照、部単位の予算承認 |

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 部(Division) | 課の上位組織。配下課の予実を合計する集計単位。**部自体は予算を策定しない** |
| 課(Department) | 予算策定の管理単位(部門)。必ず1つの部に属する |
| 半期(FiscalHalf) | 予算の策定単位。年度の上期(4〜9月)/下期(10〜3月)。表記 `yyyy-H1` / `yyyy-H2` |
| 案件(Project) | 課に属する売上・コストの内訳単位。マスタとして登録し、内部識別子は GUID |
| 費目(CostElement) | 期間費用の内訳単位(人件費・ライセンス費など)。**システム全体で共通のマスタ** |
| 区分(BudgetCategory) | 予算の構成要素。売上高・加工費・外注費(案件別)/ 期間費用(費目別)の4つ |
| 明細(BudgetLine) | 区分 × 案件、または 期間費用 × 費目 の金額。半期一括または月次(1..6月)で入力 |
| バージョン | 予算の版。当初(v1)→改定(v2…)。承認すると編集不可 |
| 課承認 | 課がその半期予算を確定する承認(Draft→Approved) |
| 部承認 | 部長が配下課の予算をまとめて確定する承認。課承認とは独立し取り消せる |
| 差異 | 実績金額 − 予算金額(符号付き) |

## 3. 機能要件(Functional Requirements)

各要件に ID(`FR-x.y`)を付す。優先度は MoSCoW(Must/Should/Could)。
「実装済み」は 2026-07-18 時点で本リポジトリに存在することを示す。

### FR-1. 組織管理(部・課)

| ID | 要件 | 優先度 | 状態 |
|---|---|---|---|
| FR-1.1 | 部を部コード(一意)・部名で登録・一覧・参照できる | Must | 実装済み |
| FR-1.2 | 部名を変更できる(部コードは識別に用いる) | Should | 実装済み |
| FR-1.3 | 課を、所属する部・課コード(一意)・課名で登録・一覧・参照できる | Must | 実装済み |
| FR-1.4 | 課は必ず1つの部に属し、部を横断して所属を変更しない | Must | 実装済み |

### FR-2. 案件マスタ

| ID | 要件 | 優先度 | 状態 |
|---|---|---|---|
| FR-2.1 | 課に属する案件を案件コード・案件名で登録できる | Must | 実装済み |
| FR-2.2 | 案件コードは**課ごとに一意**(別の課では同じコードを使える) | Must | 実装済み |
| FR-2.3 | 登録済み案件のコード・名称を後から編集できる。編集しても既存の予算・実績の紐づけは保持される(参照は GUID) | Should | 実装済み |
| FR-2.4 | 案件はライフサイクル状態(終了等)を持たない | Must | 実装済み |

### FR-3. 費目マスタ

| ID | 要件 | 優先度 | 状態 |
|---|---|---|---|
| FR-3.1 | 期間費用の費目を費目コード・費目名で登録・一覧できる(システム共通) | Must | 実装済み |
| FR-3.2 | 初期費目として人件費(`PERSONNEL`)・ライセンス費(`LICENSE`)をシードする | Must | 実装済み |
| FR-3.3 | 費目マスタは専用画面で管理し、課の予算編集からは選択のみ行う | Should | 実装済み |

### FR-4. 半期予算の策定

| ID | 要件 | 優先度 | 状態 |
|---|---|---|---|
| FR-4.1 | 課 × 半期でドラフト予算を作成できる(予算名を付与) | Must | 実装済み |
| FR-4.2 | 予算は**売上高・加工費・外注費・期間費用の4区分**からなる | Must | 実装済み |
| FR-4.3 | 売上高・加工費・外注費は**案件別明細**として金額を入力する(案件必須・費目不可) | Must | 実装済み |
| FR-4.4 | 期間費用は**費目別明細**として金額を入力する(費目必須・案件不可) | Must | 実装済み |
| FR-4.5 | 課の区分合計は**常に明細の合計として導出**され、課レベルの直接入力はできない | Must | 実装済み |
| FR-4.6 | 明細は半期一括の金額を基本とし、**明細ごとに月次(半期内 1..6 月)入力**もできる。半期合計=月次の合計として自動算出され、月次にした明細は半期一括入力を無効化する | Should | 実装済み |
| FR-4.7 | 明細キー(区分 × 案件、または 期間費用 × 費目)は予算内で一意。同一キーの入力は上書き(Upsert) | Must | 実装済み |
| FR-4.8 | 金額は 0 以上でなければならない | Must | 実装済み |
| FR-4.9 | 計画損益(売上高 − 総コスト)と粗利率(損益 ÷ 売上高)をサマリに表示する | Should | 実装済み |

### FR-5. 予算の承認・改定(バージョン管理)

| ID | 要件 | 優先度 | 状態 |
|---|---|---|---|
| FR-5.1 | 明細が1件以上あるドラフト予算を承認できる(明細なしは承認不可) | Must | 実装済み |
| FR-5.2 | 承認済み予算は編集できない | Must | 実装済み |
| FR-5.3 | 同一(課 × 半期)のドラフトは同時に1件まで | Must | 実装済み |
| FR-5.4 | 改定は、引継ぎ元バージョンの明細をすべてコピーした新バージョンのドラフトとして起票する | Must | 実装済み |
| FR-5.5 | 改定版を承認すると、同一(課 × 半期)の旧承認版は自動的に「失効(Superseded)」になり、履歴として残る | Must | 実装済み |
| FR-5.6 | 予算の状態遷移は Draft → Approved → Superseded のみ | Must | 実装済み |

### FR-6. 実績計上

| ID | 要件 | 優先度 | 状態 |
|---|---|---|---|
| FR-6.1 | 課 × 半期に対し、区分 × 案件(または 期間費用 × 費目)で実績金額を計上できる | Must | 実装済み |
| FR-6.2 | 同一キーに**複数回計上**でき、分析時に合算される | Must | 実装済み |
| FR-6.3 | 実績に計上月(1..6)を任意で指定できる(半期一括は未指定) | Should | 実装済み |
| FR-6.4 | 予算にない案件・費目の実績も計上でき、分析では「予定外」として表示される | Should | 実装済み |
| FR-6.5 | 実績を削除できる(訂正は削除して再計上) | Must | 実装済み |
| FR-6.6 | 実績に備考を任意で付与できる | Could | 実装済み |

### FR-7. 差異分析

| ID | 要件 | 優先度 | 状態 |
|---|---|---|---|
| FR-7.1 | 差異 = 実績金額 − 予算金額 を、(区分 × 案件)/(期間費用 × 費目)の粒度で突き合わせる | Must | 実装済み |
| FR-7.2 | 符号規則: コスト(加工費・外注費・期間費用)は正=不利、売上高は正=有利 | Must | 実装済み |
| FR-7.3 | 区分ごとのサブトータル(予算・実績・差異)を表示する | Must | 実装済み |
| FR-7.4 | 予算にない実績を「予定外」として表示する | Should | 実装済み |
| FR-7.5 | 分析・集計は**半期粒度**で行う(月次入力は半期合計に畳んで比較する) | Must | 実装済み |
| FR-7.6 | 基準とする予算バージョンを切り替えて比較できる(旧版基準の予実比較) | Should | 実装済み |

### FR-8. 損益分析

| ID | 要件 | 優先度 | 状態 |
|---|---|---|---|
| FR-8.1 | 課全体の損益 = 売上高 −(加工費 + 外注費 + 期間費用)を予実で表示する | Must | 実装済み |
| FR-8.2 | 案件別の損益 = 売上高 − 加工費 − 外注費(期間費用は課共通のため案件に配賦しない) | Must | 実装済み |
| FR-8.3 | 「案件別損益の合計 − 期間費用 = 課全体の損益」が常に成立する | Must | 実装済み |
| FR-8.4 | 損益に粗利率(損益 ÷ 売上高、売上高0は非表示)を併記する | Should | 実装済み |

### FR-9. 予算バージョン比較

| ID | 要件 | 優先度 | 状態 |
|---|---|---|---|
| FR-9.1 | 基準バージョンと比較バージョンを選び、区分別・明細別の増減を表示する | Should | 実装済み |

### FR-10. 部集計・部承認

| ID | 要件 | 優先度 | 状態 |
|---|---|---|---|
| FR-10.1 | 部詳細で配下課の予算(4区分・計画損益・粗利率)を集計参照できる(予算(計画)タブ) | Must | 実装済み |
| FR-10.2 | 課ごとの予算比較をグリッドで並べ、損益・粗利率を色分けし、弱い課を把握できる | Should | 実装済み |
| FR-10.3 | 部詳細で配下課の予実差異を集計参照できる(予実サマリタブ) | Must | 実装済み |
| FR-10.4 | 承認済み予算のない課は「未策定」として内訳表示し、部合計には含めない(部合計 = 課別内訳の合計) | Must | 実装済み |
| FR-10.5 | 配下課がすべて承認済みのとき、部単位の予算承認ができる。取り消しもできる | Should | 実装済み |
| FR-10.6 | 部承認は課の承認と独立し、部承認後に課を改定しても部承認は残る | Should | 実装済み |

## 4. 非機能要件(Non-Functional Requirements)

### NFR-1. 性能

| ID | 要件 |
|---|---|
| NFR-1.1 | 通常の画面操作(一覧・詳細・保存)は、単一課・単一半期の規模(案件数十件・実績数百件)で体感遅延なく応答すること |
| NFR-1.2 | 明細のセル入力は、フォーカスを外した時点で自動保存され、都度の全画面再読込を要しないこと |
| NFR-1.3 | 分析(差異・損益・比較・部集計)はステートレスに算出し、事前集計テーブルを持たないこと(整合性優先) |

### NFR-2. 信頼性・データ整合性

| ID | 要件 |
|---|---|
| NFR-2.1 | 集約の不変条件(4区分1承認、承認済み編集不可、明細キー一意、区分合計=明細合計、金額0以上、区分と案件/費目の排他)を**ドメイン層で強制**すること([DESIGN.md](DESIGN.md) の不変条件表) |
| NFR-2.2 | 不変条件違反は `DomainException`(日本語メッセージ)として送出し、API は HTTP 400 に、未検出は 404 に変換すること |
| NFR-2.3 | 「案件別損益の合計 − 期間費用 = 課全体の損益」「部合計 = 課別内訳の合計」等の整合性は自動テストで担保すること |
| NFR-2.4 | サーバーレス構成では SQLite への同時書き込みを直列化すること(Lambda 予約同時実行 = 1。ADR-0010) |

### NFR-3. セキュリティ

| ID | 要件 |
|---|---|
| NFR-3.1 | 入力値はドメイン層で検証し、不正値を集約に取り込まないこと |
| NFR-3.2 | 永続化は Dapper のパラメータバインドを用い、SQL 文字列連結を行わないこと(SQLインジェクション防止) |
| NFR-3.3 | 認証・認可は現状スコープ外。将来導入する場合は WebApi 層(入力アダプタ)に差し込み、ドメイン層を汚さないこと |
| NFR-3.4 | 秘密情報(接続情報・トークン等)をリポジトリ・コミット・ログに含めないこと |

### NFR-4. 保守性・拡張性

| ID | 要件 |
|---|---|
| NFR-4.1 | ヘキサゴナル(ポート&アダプタ)+ DDD 戦術パターンを採用し、依存は常に内側(Domain)へ向けること。Domain は他のどの層にも依存しないこと(ADR-0001) |
| NFR-4.2 | 層間の依存規則(Domain 非依存、リポジトリ実装は Infrastructure のみ 等)を**アーキテクチャテスト(NetArchTest)で強制**すること |
| NFR-4.3 | 集約ルート・エンティティ・ドメインサービスは `sealed`、値オブジェクトは `readonly record struct`、公開セッターを置かないこと |
| NFR-4.4 | ポート数・値オブジェクト列挙・集約列挙はアーキテクチャテストに固定値で書き、構成変更時に同時更新すること |
| NFR-4.5 | backend/src の全クラス・メソッドに日本語の XML ドキュメントコメントを付すこと |

### NFR-5. テスト容易性・品質

| ID | 要件 |
|---|---|
| NFR-5.1 | テストは 5 種(Domain / Application / Infrastructure / API E2E / Architecture)+ ブラウザ E2E(Playwright)で構成すること |
| NFR-5.2 | テスト名・エラーメッセージ・コミットメッセージは**日本語**とし、テスト一覧が仕様書として読めること |
| NFR-5.3 | 行カバレッジは全体 85% 以上を維持し、CI の実行サマリで可視化すること(現状 89.9%) |
| NFR-5.4 | **ミューテーションテスト(Stryker.NET)**で Domain・Application 層のテスト有効性を測定し、CI でレポートを出力すること(非ブロッキング。ADR-0011) |

### NFR-6. 移植性・デプロイ・可用性

| ID | 要件 |
|---|---|
| NFR-6.1 | ローカルは Docker(または .NET/Node の SDK)でビルド・テスト・起動できること |
| NFR-6.2 | クラウドは EC2・コンテナを使わないサーバーレス構成(Lambda + EFS + S3 + CloudFront)を IaC(AWS SAM)で提供し、費用を抑えること(ADR-0010) |

| ID | 要件 |
|---|---|

| NFR-7.3 | 金額は 3 桁カンマ区切りで表示・入力すること |

### NFR-8. ユーザビリティ・アクセシビリティ

| ID | 要件 |
|---|---|
| NFR-8.1 | エラーは画面右下の固定トーストで通知し、一定時間で自動的に消えること(ADR-0012) |

## 5. アーキテクチャ制約(Architecture Constraints)

以下は設計・実装で**必ず守る制約**。個々の背景と根拠は [ADR](adr/README.md) に記す。

| ID | 制約 | 根拠 |
|---|---|---|
| AC-1 | 依存は常に内側(Domain)へ。Domain は他層に依存しない。リポジトリはドメイン層のポート(interface)として定義し、実装は Infrastructure 層のみに置く | ADR-0001 |
| AC-2 | 予算の管理単位は**課 × 半期の単一集約(DepartmentBudget)**。プロジェクト単位予算・売上と原価の別集約は復活させない | ADR-0002, ADR-0004 |
| AC-3 | 明細は**金額のみ**。数量 × 単価、価格差異/数量差異の分解は導入しない | ADR-0003 |
| AC-4 | 課の区分合計はヘッダに持たず、**常に明細の合計として導出**する(直接入力を構造的に不可にする) | ADR-0005 |
| AC-5 | 組織は**部 > 課の2階層**。部は予算を持たない集計ビュー。部承認は独立集約とし課承認フローに手を入れない | ADR-0006 |
| AC-6 | 永続化は SQLite + Dapper。旧世代スキーマは**データ移行せず破棄・再作成**。現世代内の変更のみデータ保持マイグレーション(冪等) | ADR-0007 |
| AC-7 | 他集約は案件を **ProjectId(GUID)** で参照する。案件コードは課ごとに一意で編集可能 | ADR-0008 |
| AC-8 | 月次入力は**入力の内訳**にとどめ、集計・差異・損益・部集計はすべて**半期粒度**で行う | ADR-0009 |
| AC-9 | 分析はステートレスなドメインサービス + イミュータブルな record レポートで実現する | ADR-0001 |
| AC-10 | 開発ブランチは `claude/cost-management-system-qvc368`。main へ直接プッシュしない。PR は明示依頼時のみ | — |
