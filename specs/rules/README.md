# 処理ルール(specs/rules/)

計算・判定・状態の変化を、実装が一通りに決まるところまで書く。1 ルール 1 ファイル(`SPEC-<連番 3 桁>.md`)。
番号は使い回さない。廃止したら `status: 廃止` にする。

## ファイルの形

```markdown
---
id: SPEC-001
title: 明細の金額の検証
status: 有効                  # 有効 | 廃止
requirements: [FR-4.8]        # 満たす要件
business_rules: [BR-BUD-007]  # 元にした業務ルール
api:                          # 関係する API(メソッドとパス)
  - PUT /api/budgets/{budgetId}/lines
issues: [46]
---

## ルール

入力・判定・出力を、デシジョンテーブル・計算式・状態遷移表のどれかで書く。
エラーにするときは、HTTP ステータスとメッセージ(日本語)を書く。

## 具体例

| # | 入力 | 期待する結果 | 境界の理由 |
|---|---|---|---|
| 1 | 金額 0 | 保存される | 下限ちょうど |
| 2 | 金額 -1 | 400「金額は0以上で入力してください。」 | 下限の 1 つ下 |

## テストの観点

| 観点 | テストレベル | 置き場所 |
|---|---|---|
| 金額の下限 | 単体(Domain) | `tests/unit/backend/Domain` |
| 拒否したとき既存の明細が変わらない | 結合(Gherkin) | `tests/integration/backend/Application/Features/…` の `@FR-4.8` |
| 400 とメッセージの形 | API E2E | `tests/e2e/api/Features/APIのエラー応答.feature` |
```

- 具体例の各行は、どれかのテストで確かめる。確かめないなら、その行は書かない
- エラーメッセージは、ドメインの `DomainException` の文言と一字一句合わせる(テストが文言で検証するため)
- 画面の見た目・文言の配置は書かない(画面要件が正)
