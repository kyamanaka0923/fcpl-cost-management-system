# テスト計画

テストレベルごとに、何を母集団にし、何をもって完了とするかを決める(PROC-DEV-001 3.2、4.3)。
テストの置き場所と道具は [ADR-0016](../docs/adr/0016-test-scope-layout-and-frontend-unit.md)、
カバレッジとミューテーションの方針は [ADR-0011](../docs/adr/0011-testing-strategy-and-mutation.md)、実行方法は [README.md](../README.md) の「テスト」。
作業項目ごとのテストの観点は、各処理ルール([rules/](rules/README.md))の「テストの観点」に書く。

## 大原則

- **テストは要件・仕様から導く。** コードを読んでテストを作らない。
  シナリオは要件の `.feature`、例示テストは処理ルールの「具体例」、プロパティは業務ルールの不変条件から作る
- テスト名は日本語の文にし、一覧が仕様書として読めるようにする
- 速いテストで確かめられることは速いテストで確かめる。E2E は部品のつながりの確認に絞る

## レベルごとの母集団と完了基準

| レベル | 置き場所 | 母集団(何を全部確かめるか) | 完了基準 |
|---|---|---|---|
| 単体(Domain) | `tests/unit/backend/Domain` | 処理ルールの具体例の表の行、業務ルールの不変条件 | 具体例の全行にテストがある。不変条件は CsCheck のプロパティで確かめる |
| 単体(フロントエンド) | `tests/unit/frontend` | 画面だけの振る舞い(入力チェック・表示の書式・送るリクエストの中身・トースト) | 画面要件の表示の条件と操作に、それぞれテストがある |
| 結合(Application) | `tests/integration/backend/Application` | 移した要件(`requirements/`)すべて | 移した要件の全件に `@FR-x.y` のシナリオがあり、すべて Passed(Skipped 0) |
| 結合(Infrastructure) | `tests/integration/backend/Infrastructure` | 永続化する集約と列、スキーマの変更 | 集約ごとに保存して読み戻すテストがある。スキーマを変えたら作り直しの冪等性のテストがある |
| API E2E | `tests/e2e/api` | WebAPI 仕様の各操作の正常系と、エラーの HTTP ステータスの種類 | OpenAPI 定義との一致テストが通る。新しい操作に正常系とエラー系のシナリオがある |
| ブラウザ E2E | `tests/e2e/browser` | 主要な業務の流れ(計画策定・予算明細の入力・実績と分析・マスタ管理) | 流れが通しで動く。画面の細かい分岐はここに足さない |
| 構造 | `tests/architecture/backend` | 層の依存ルール(AC-1)とドメインの規約 | 依存しないことの検査に、検出器が働いていることのポジティブコントロールがある |

## 全体の基準

| 指標 | 基準 | 扱い |
|---|---|---|
| CI の必須ジョブ | すべて成功 | マージの条件(main のルールセット) |
| 行カバレッジ(バックエンド全体) | 85% 以上(いまは 89.9%) | CI の実行サマリで確かめる。下回ったら原因を作業項目にする |
| ミューテーションスコア(Domain・Application) | 目標 80%(Stryker の high)。60% 未満(low)は要改善。いまはどちらも約 54% | **マージの条件にしない**(CI では非ブロッキング)。週報で推移を見る |
| 要件の網羅 | 移した要件すべてにシナリオがあり、存在しない要件を指すタグがない | CI の「要件とシナリオの網羅」(必須チェック) |
