# レビューの観点

レビューするエージェント(`requirements-reviewer`・`code-reviewer`)と人が、ゲートで見る観点。
新しい観点は、介入の記録(人が直した原因)から足す。

## 共通(要件・仕様)

- [ ] 要件文は EARS の文型の 1 文で、応答は 1 つか。曖昧な言葉(適切に・など・柔軟に・必要に応じて)がないか
- [ ] 境界(0・上限・空・未入力)が Gherkin の例で数値として決まっているか
- [ ] 業務ルール(`BR-…`)と矛盾しないか。参照している業務ルールは `status: 確定` か
- [ ] 例外のルート(拒否されるとき・失敗したとき)のメッセージと結果が書かれているか
- [ ] 戻せない操作(承認・失効)の前後で何が変わり、何が変わらないかが書かれているか
- [ ] 画面の文言・配置を Gherkin に書いていないか(画面要件に書く)

## この業務に特有のもの

- [ ] **承認済み・失効済みの予算を変えていないか**(変えるなら改定版で。BR-BUD-002)
- [ ] **区分合計を明細以外から作っていないか**(BR-BUD-004)
- [ ] **区分と案件・費目の組み合わせ**の拒否がそろっているか(BR-BUD-003)
- [ ] **費目一括と明細名ありの混在**を許していないか(BR-BUD-006)
- [ ] **集計を月次の粒度でしていないか**(月次は入力の内訳だけ。BR-FH-001)
- [ ] **差異の符号**が規則どおりか。「有利/不利」の言葉を使っていないか(BR-VAR-001)
- [ ] 「案件別損益の合計 − 期間費用 = 課の損益」「部合計 = 課別内訳の合計」が崩れないか(BR-PL-001、BR-DIV-001)
- [ ] 数量 × 単価を持ち込んでいないか(BR-BUD-007)

## 実装(ゲート3)

- [ ] 依存の向き(Domain は外側に依存しない)を守っているか。アーキテクチャテストを弱めていないか
- [ ] 不変条件をドメイン層で強制し、違反は日本語の `DomainException` で返しているか(API では 400)
- [ ] テストは要件・仕様から導いたものか(コードの写しになっていないか)。テスト名は日本語の文か
- [ ] スキーマを変えたとき、作り直し・冪等性・既存データの保持のテストがあるか
- [ ] SQL はパラメータバインドか。秘密情報をコミット・ログに出していないか
